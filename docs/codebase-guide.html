scion-hev3 — Codebase Guide

Happy Eyeballs v3 with SCION as a third address family: a racing client library, CLI, and demo server, plus the IETF drafts that define how it all works on the wire.

What this project is. pkg/hev3 implements draft-ietf-happy-happyeyeballs-v3-04 extended with SCION: it resolves a name via HTTPS/SVCB (including the scion= SvcParam), AAAA and A, builds a candidate list spanning three families (SCION, IPv6, IPv4), and races connection attempts with HEv3 staggering — first successful connection wins. cmd/hev3 is the CLI front-end (hev3 https://web.scion/); cmd/hev3-server is the demo target that serves the same page over every transport and tags each response with the transport that delivered it. Two companion drafts: draft-john-scion-svcb (netsys-lab/draft-scion-svcb) defines the scion SvcParamKey (discovery; Private Use key 65280 until IANA assigns one), and draft-john-scion-happy-eyeballs (netsys-lab/draft-scion-happy-eyeballs) defines the client algorithm this library implements: path lookup per SCION endpoint, a ranked path set of up to K paths, racing those paths within one QUIC connection, three-family sorting, the Expansion Delay, and failing paths on SCMP errors. Built for the SCION testbed at the IETF 126 hackathon.

Note (separate path attempts, November 2026). This guide predates the current default design and has not been rewritten. Now: a SCION address is one endpoint; an attempt selects up to Path Attempt Count paths (-k, default 2) when it starts and opens a separate QUIC connection on each, one Path Attempt Delay (-path-attempt-delay, 50 ms) apart (attempts.go). The Expansion Delay is gone: the path lookup is shared per ISD-AS (lookupGroup in dial_scion.go) and a SCION-first client waits for it no longer than the Resolution Delay (25 ms) after the first IP answer (lookupWait, holdForGrace in engine.go). SCMP errors are recorded and do not end an attempt. -family-order ip-first puts SCION last. The racer described in §8 (racer.go, -path-delay) is what -path-mode copy still runs; -expansion-delay no longer exists. The README has the current summary.

Note (path racing rework). Sections below that predate the rework may still say "per-path candidates #p1..#pK": a SCION endpoint is now one candidate (<parent>#paths) carrying its ranked PathSet; see §8.

How to read this guide. Section 2 gives the end-to-end picture — read it first; everything later hangs off its two diagrams. Sections 3–14 are per-file deep dives ordered roughly by data flow (types → resolver → engine → dialers → CLI/server); each names its file and key functions so you can jump straight into the source. Section 15 collects what cuts across files: the test seams, the two forked dependencies the build depends on, and the invariants that are easy to break when refactoring. Section 16 is a glossary of project jargon. Every claim in this guide was written against the actual code on this branch; function names are given instead of line numbers because lines drift.

2. Architecture overview

2.1 The Fetch pipeline pkg/hev3/hev3.go

hev3.Fetch is the whole pipeline: resolve → engine (live merge + async expansion + sort + staggered racing) → winner GET. Unlike a textbook HEv3 flow that resolves, sorts once, and races a fixed list, the engine here is a single-goroutine scheduler that keeps merging two asynchronous inputs into a running race: the resolver's Updates channel (later DNS answers) and expander goroutines (SCION path lookup results). The diagram below shows the real data flow — every box is a concrete type or function.

Reading the diagram: ResolveHost hands the engine an Initial candidate set (gated by the §4.2 Resolution Delay) and then streams later complete sets on Updates. The engine ingests each set into its candidate table; SCION candidates arrive as proto-candidates (FamilySCION, Path == nil) that are not dialable yet, so ingest hands each to an expander goroutine (ExpandSCION) instead of the pending list. Expansion results come back as expandResults whose child (one native candidate #paths carrying the endpoint's ranked path set, or one scitra fallback) enter the table like any other candidate. Every ingest re-sorts the complete live set (Sort), so a late arrival is positioned as if it had been present from the start. Launches are staggered by the attempt-delay timer; each launched attempt is one goroutine calling the DialFunc, which dispatches to one of three dialer families. First success cancels everything else and the winning *Established carries the single GET. Every stage appends to the shared Timeline, which the CLI renders as the race table.

2.2 Engine state machine pkg/hev3/engine.go

Each table entry has one of six statuses. Only the engine loop goroutine mutates them, so there are no locks — attempt and expansion goroutines communicate exclusively through the results and expandResults channels.

Two subtleties the diagram encodes: (1) a tombstone is candDone with cancel == nil && err == nil — that exact triple is what resort tests to exclude tombstones from the live list; (2) proto parents (candExpanding/candExpanded) are placeholders that never appear in the sorted live list — only their children race.

3. types.go — Candidate anatomy pkg/hev3/types.go

The whole pipeline trades in one currency: Candidate, one dialable destination.

type Candidate struct {
    Family    Family      // FamilySCION | FamilyIPv6 | FamilyIPv4
    Host      string      // IP literal, or SCION host IP
    Port      uint16
    IA        string      // "1-150"; empty for IP families
    Path      *SCIONPath  // = &PathSet[0]; nil for IP families, the scitra leg, and protos
    PathSet   []SCIONPath // SCION endpoint's ranked path set (K paths max), raced in one QUIC conn
    ViaScitra bool        // SCION-derived candidate dialed as mapped IPv6
    ALPN      []string    // dial ALPN; empty = default (try h2/h1.1 over TCP)
    GroupALPN []string    // covering record's full ALPN set — §5.1 grouping key
    Priority  uint16      // SvcPriority
    Label     string      // stable human id, e.g. "scion:1-150,10.0.0.1#paths", "v6:2001:db8::1"
}
  • Label is identity. The engine's table, the resolver's candidate-event dedup (emitNewCandidates), and the CLI's race rows are all keyed by Label. Labels follow fixed prefixes — scion:, scitra:, v6:/v6hint:, v4:/v4hint:, with +tcp inserted for TCP siblings and #paths appended by path expansion — and cmd/hev3's familyFromLabel relies on exactly these prefixes.
  • GroupALPN vs ALPN. ALPN is what the dialer offers (["h3"] for a QUIC leg; supported-minus-h3 for its TCP sibling). GroupALPN is the covering record's full supported set and is the §5.1 grouping key in Sort — it keeps a record's QUIC and TCP candidates in the same group so racing is per-address QUIC-before-TCP, not all-QUIC-then-all-TCP. nil GroupALPN (legacy no-record and unassociated-trailing candidates) falls back to grouping by ALPN.
  • ViaScitra marks a SCION-derived candidate rewritten to a mapped IPv6 address; it is FamilyIPv6 for sorting/interleave purposes but keeps IA and a scitra: label.
  • PathSet/Path (SCIONPath: fingerprint, summed declared latency, AS hops, interface string, down-cache flag, and the snet.Path stored as any so pure-logic files need no scionproto import). Path points at the top-ranked path and distinguishes an expanded SCION endpoint from a proto-candidate (Path == nil). "Any native (non-scitra) FamilySCION candidate" is the signal (hasSCION) that the client has SCION connectivity, which orders SCION first in Sort.

4. resolver.go — DNS to candidates pkg/hev3/resolver.go

Purpose. ResolveHost(ctx, host, port, ResolveOptions) turns one hostname into a stream of candidate sets. It launches a dynamic set of parallel queries — HTTPS and/or SVCB (per RRType), AAAA and A for the owner, and AAAA/A for every ServiceMode TargetName discovered along the way (RFC 9460 §4.2.1) — and returns Resolved{Initial, Updates}. Key internals: resolveRun.run (the event loop), resolveService/resolveIPs (per-query workers), parseServiceRecord/svcRecord (typed record view), buildCandidates/recordCandidates (candidate emission), orderRecords (§5.2 priority + shuffle).

The §4.2 release gate

The heart of run is the release closure, which decides when the current merged candidate set may be published:

allFinal := outstanding == 0
if !allFinal {
    if !positive() { return }
    if !(ownerAAAAFinal() && serviceFinal()) && !delayElapsed { return }
}
  • Positive answer required — a final non-empty AAAA/A for any queried name, or a chosen service record carrying a scion= address or an ipv4/ipv6 hint. A SCION-only name therefore counts as positive without any address answer.
  • Set 1 is "owner's AAAA final AND every queried service qtype final". A is never itself a gate requirement — only a possible source of positivity.
  • Timer arming: the Resolution Delay timer (default defaultResolutionDelay = 50ms) starts disarmed and is armed only at the first positive answer while set 1 is still unsatisfied — the draft starts the clock at the first positive response, not at query dispatch. Once it fires, delayElapsed lets the gate clear on positivity alone.
  • Unconditional release: when nothing is outstanding, release happens even with zero positive answers — an empty candidate set is a valid, immediate answer.

Record handling

  • Multi-record ServiceMode + TargetName chase. Every ServiceMode record contributes candidates carrying its own ALPN/port/priority. A record whose TargetName names a not-yet-queried host spawns AAAA/A for it mid-flight, so outstanding grows dynamically. A TargetName shared by several records has its A/AAAA emitted only by the first (lowest-priority) covering record (the emitted map in recordCandidates); later records covering the same name re-emit only their own scion= addresses. Owner addresses no record targets trail the list as "unassociated" candidates at priority 65535.
  • AliasMode chase. resolveService follows AliasMode (SvcPriority 0) chains up to maxAliasChase = 4 steps, re-querying the same qtype; a present AliasMode record suppresses ServiceMode siblings (RFC 9460 §2.4.2). Loop/self-alias detection keys on dns.CanonicalName (case-insensitive, RFC 4343), and a TargetName of "." resolves against the name that answered (the chase end), not the original owner.
  • Mandatory rejection. parseServiceRecord rejects a record whose mandatory= lists any SvcParamKey outside supportedParams (RFC 9460 §8); the record is skipped with a one-time timeline note (noteOnce), naming the offending key in the error.
  • Effective ALPN → dual candidates. svcRecord.supportedALPN computes the record's effective set — its alpn= values plus the https default http/1.1 unless no-default-alpn — intersected with clientALPN (h3, h2, http/1.1) in client preference order. Each IP address then emits up to two candidates: a QUIC candidate (ALPN ["h3"]) when h3 is supported and a TCP candidate (supported minus h3, label suffix +tcp) when anything else is — so a UDP-blackholed network still converges on h2/http1.1. A record whose effective set is empty contributes nothing at all (draft §6.2).
  • SCION requires QUIC. scion= addresses are emitted only when the record's set includes h3; otherwise each is dropped with a "no QUIC ALPN in record; SCION transport is QUIC-only" note.
  • Hint suppression. ipv4hint/ipv6hint stand in only when the corresponding family's real answer is final and empty (RFC 9460 §7.3) — a hint never overrides or supplements live A/AAAA data.
  • Equal-priority shuffle. orderRecords sorts records by SvcPriority and shuffles runs of equal priority (§5.2) with a run-stable RNG (seeded from ShuffleSeed, or 8 bytes of crypto/rand per run). It is called exactly once per qtype so rebuilds never reshuffle — a reshuffle would emit spurious Updates.
  • RRType selection. RRHTTPS (default) sends the one HTTPS query the draft specifies. RRSVCB sends an SVCB query instead. RRBoth queries HTTPS and SVCB in parallel and the chosen closure prefers the HTTPS answer's records when present; it is not in the draft and is for zones that publish only SVCB records.
  • ISD-AS presentation. scionIA recomputes the canonical form from ISD/ASN instead of calling addr.String(): the forked dns module's wire pack/unpack loses the hex-vs-decimal presentation bit, so large ("SCION-only") ASNs are printed as three hex groups by rule (ASN > maxBGPAS), keeping Label consistent with IA regardless of how the answer arrived.

Transport details

exchange/exchangeServers: every query carries EDNS0 with a 1232-byte UDP size; a truncated UDP reply triggers one TCP retry against the same server, falling back to the truncated answer if TCP fails. Servers come from resolverAddresses: a comma-separated Resolver option is tried in order (failover), otherwise every nameserver in /etc/resolv.conf, IPv6 servers first (draft §4.5). queryTimeout = 2s bounds one per-server attempt, not the end-to-end exchange.

The Resolved contract

Drain or cancel. Updates delivers complete candidate sets — each send replaces, never appends — and is closed when nothing is outstanding. A caller must keep draining Updates until it closes, or cancel ctx: the internal goroutine blocks sending a merged result with only a ctx.Done() escape, so an abandoned channel whose ctx never ends delays cleanup until the ctx's own deadline. Resolved.MinTTL reports the smallest TTL among contributing answers (via captureTTL, atomically min-tracked) — the natural cache lifetime for the set; zero until a positive answer.

5. engine.go — the connection engine pkg/hev3/engine.go

Purpose. runEngine(ctx, engineConfig) is the §4–§7 scheduler: one goroutine (engine.loop) owning the candidate table, the sorted pending list, and both timers. engineConfig's zero-value fields disable features (nil updates ⇒ static set; nil sortFn ⇒ insertion order; nil filter ⇒ accept all; nil isProto/expand ⇒ no expansion interception), which is exactly how Race degenerates it.

Ingest and resort (§4.3/§7 merge)

  • ingest(set) merges one complete set: filtered candidates are dropped before anything else; known labels keep their status (first ingest wins); proto candidates (isProto) get a candExpanding entry and one expander goroutine; everything else enters as candNew.
  • Tombstones. In dynamic mode (updates non-nil), labels still candNew whose label — or, for expanded children, whose parent proto label — is missing from the set are marked candDone: never launched, never will be (§7: started attempts are never cancelled by a DNS change). An empty update set legitimately tombstones every unlaunched candidate (a late no-supported-ALPN record can revoke the whole set, draft §6.2). Tombstones are permanent: ingest skips known labels, so a re-added label never resurrects, and a re-added proto parent never re-expands.
  • resort() rebuilds pending: the sort function sees the complete live list (all statuses except proto placeholders and tombstones) so a late arrival is positioned as if present from the start; pending is then the sorted order filtered to candNew.

Memoized async expansion

The candExpanding table entry does double duty: it memoizes the label — a re-send of the same proto by a later update finds the entry and never re-expands, which keeps Timeline drop-notes single (the guarantee the deleted expandCached helper used to provide) — and it gives §7 child-removal a parent to test membership against. Expander goroutines dial against e.expandCtx, cancelled the instant loop returns on any path, so an expander can neither outlive the engine nor block writing to the buffer-8 expandResults channel after nobody reads it. When a result arrives, children are ingested without re-filtering (see the invariants section) and the parent flips to candExpanded. A proto tombstoned while its expansion was in flight still gets its children ingested — self-healing rather than a bug, because the resolver always re-sends complete sets and the next update's §7 pass re-tombstones those children.

Stagger timer discipline

Both timers use the disarmed-start pattern (NewTimer(hour), immediate Stop + drain), with arm/disarm helpers that drain the channel to prevent stale ticks. launchNext pops the pending head, launches it, and arms the stagger for the next candidate with nextDelay — or disarms when pending is empty. Two re-arm paths exist for "fresh candidates entered pending while no stagger clock is ticking": one after expandResults ingestion and one after an updates ingestion. Both distinguish inflight == 0 (nothing to stagger against — launch immediately; the expansion path also covers lastLaunched == "", the proto-only-initial-set case where nothing was ever launched) from "an attempt is in flight but the timer was disarmed" (a §4.3 update emptied pending under an armed timer; re-arm relative to now so new arrivals launch within one normal interval instead of being stranded until the in-flight attempt finishes).

Adaptive delay

Off by default and not in the draft; -adaptive-delay turns it on.

// nextDelay: clamp(2·Latency + 60ms, minDelay, base)
d := e.cfg.delay
if e.cfg.adaptive && c.Family == FamilySCION && c.Path != nil && c.Path.Latency > 0 {
    if a := 2*c.Path.Latency + 60*time.Millisecond; a < d {
        d = a
        if d < e.cfg.minDelay { d = e.cfg.minDelay }
    }
}
if d > e.cfg.delay { d = e.cfg.delay } // final re-cap

After launching a SCION endpoint whose top path has known latency L, the next stagger tightens to clamp(2L+60ms, minDelay, base) — the shortcut can only shorten the base stagger, never lengthen it; the final re-cap guarantees that even a misconfigured minDelay above base cannot drag the next attempt out. runEngine's defaulting establishes the bounds first: base delay ≤0 ⇒ 250ms, min ≤0 ⇒ 100ms, max ≤0 ⇒ 2s, and everything is hard-floored at minAttemptDelayFloor = 10ms (the draft §6 MUST — an explicit sub-10ms cap cannot defeat the floor) with the base capped at max.

Expansion Delay

holdForGrace(lbl) implements the Expansion Delay of draft-john-scion-happy-eyeballs: it holds a launch when the delay is configured (expansionDelay > 0; Fetch defaults it to 50ms, negative disables), the window hasn't closed (!graceOver), no IP attempt has started yet (!ipLaunched - only the first IP attempt is held), a path lookup is in flight (expanding > 0), the pending head is not SCION, and an endpoint whose lookup is in flight would sort before the head (expandingPrecedes). While held, the grace timer is armed once and the stagger stays disarmed; lookups completing or the timer firing release the head. graceOver is one-way. CLI: -expansion-delay (0 = off).

SCION attempt failure

When the most recent attempt fails, the next pending candidate launches without waiting for the stagger. After a failed SCION attempt (e.g. every path of its set failed on SCMP errors), the launch is deferred to at least minDelay (the Minimum Connection Attempt Delay) after the failed attempt started (lastStart).

Terminal conditions

  • Success: first error-free attemptResult ⇒ finish: timeline success+winner, cancel every other in-flight attempt (timeline cancel), spawn drainClose to reap straggler results (a connection that won its dial after losing the race gets closed, not leaked), and wrap the winner in withCancelOnClose so its dial-context cancel is deferred until the caller closes the connection.
  • Failure: the loop's guard — inflight == 0 && len(pending) == 0 && sourcesDone(), where sourcesDone is "updates closed and no expansion in flight" — returns failure(): joined per-label errors in insertion order ("hev3: all N candidates failed: …"), or the caller's noCandsErr when nothing was ever attempted.
  • Fail-and-promote (§6): a failing attempt that is the most recently launched one promotes the next pending candidate immediately (disarm + launchNext).
  • ctx cancelled: cancel all in-flight, drain their results (in-flight can exceed the 64-slot results buffer in dynamic mode, so the drain is required for goroutine hygiene), return ctx.Err().

6. race.go — static-set wrapper pkg/hev3/race.go

Race(ctx, cands, dial, RaceOptions) is a thin wrapper over runEngine with every dynamic feature off: no updates, no sortFn (attempts start in list order — the caller has already sorted), no filter, no isProto/expand. It pre-checks the empty list ("hev3: no candidates to race") and passes the delay knobs through. What it pins is behavioral parity: the §6 semantics (stagger, most-recent-failure promotion, first success cancels the rest, straggler close, joined all-failed error) are identical whether the engine is driven statically by Race or dynamically by Fetch — race_test.go exercises those semantics against this entry point. This file also owns defaultAttemptDelay (250ms) and the core dial types: Established{Cand, RT, Close, ALPN} and DialFunc.

7. sort.go + rfc6724.go — ordering pkg/hev3/sort.go, pkg/hev3/rfc6724.go

Purpose. Sort(cands, nativeSCION, preferredFamilyCount) implements draft §5 extended to three families. The stages, in order:

  1. Group by ALPN set (groupByALPN): candidates whose ALPN slice is set-equal (order/duplicates ignored) share a group, keyed off GroupALPN when present so one record's QUIC and TCP siblings stay together (see §3). Groups sort ascending by their best (lowest) member Priority, first-seen order breaking ties.
  2. Within each group, bucket by family. Each group is first split by service priority, lowest value first. The SCION endpoints of one priority are ordered at random among themselves (one random order per process, so sorting again keeps it), with endpoints still in path lookup last. IP buckets go through sortIPBucket.
  3. Family interleave (sortPriorityGroup): with native SCION (nativeSCION = any native FamilySCION candidate; scitra legs don't count) the preference order is SCION, then the family of the first IP endpoint after RFC 6724 ordering of the IPv6 and IPv4 buckets together (firstIPFamily), then the other IP family; without it, IPv6 then IPv4, with any stray FamilySCION candidate appended last rather than interleaved. The first family takes preferredFamilyCount endpoints (the CLI's -pfc) at the start of the list only; after that every family takes one in turn — RFC 8305 §4's interleave generalized to N families. ViaScitra candidates are FamilyIPv6 and interleave normally.

sortIPBucket — a five-level strict weak ordering

One comparator, fully lexicographic, each level a total preorder so the composition satisfies sort.SliceStable's strict-weak-ordering contract:

  1. (a) ascending Priority (§5.1);
  2. (b) scitra legs after real ones — before the RFC 6724 comparison, a reviewed subtlety: a translator leg must never beat a genuine IPv6 address on 6724 grounds;
  3. (c) RFC 6724 §6 order between distinct addresses (§5.3 MUST);
  4. (d) same-Host candidates grouped contiguously in first-seen order — this level exists to make address-equality itself an ordered level; an earlier version that applied (e) only "when hosts are equal" produced an intransitive relation (a1-h3 ~ a2-h3 and a2-h3 ~ a1-tcp yet a1-h3 < a1-tcp) and could corrupt the sort;
  5. (e) same address: QUIC (offers h3) before TCP.

rfc6724.go implements the subset of RFC 6724 §6 destination-address selection that §5.3 requires: rules 1 (reachable first), 2 (matching scope), 6 (higher precedence, via the §2.1 default policy table), 8 (smaller scope) and 9 (longest common prefix with the chosen source), composed in rfc6724Cmp over per-address rfc6724Keys. Rules 3–5, 7 and 10 need per-interface state the library doesn't track; rule 10 (leave order) is the stable-sort fallback. The source address for rules 1/2/9 comes from udpSource — the connected-UDP trick (dial UDP to dst:53; no packets leave the host; the kernel picks the source) — a package var so tests inject fixed sources. Unparseable hosts get the zero key: a stable fallback.

8. dial_scion.go — expansion & native dial pkg/hev3/dial_scion.go

ExpandSCION

ExpandSCION(ctx, cands, DialerOptions) turns proto-candidates (FamilySCION, Path == nil, !ViaScitra) into dialable ones; everything else passes through unchanged. Three outcomes per proto:

  • Live daemon ⇒ expandOne: parse the IA, query paths, select the ranked path set (selectPathSet, pathset.go; K default 3), and emit one candidate labelled <parent>#paths with PathSet in rank order. Lookup time, daemon setup time, paths found, set and exclusions go to LookupStats.
  • No daemon (querier resolution failed) ⇒ fallbackNoDaemon: if scitraAvailable(), each proto becomes one ViaScitra candidate (scitraCandidate: FamilyIPv6, host rewritten via ScitraMap, label scitra:<IA>,<mapped>); otherwise dropped with a "no SCION daemon and no scitra route" timeline note.
  • Daemon present but no usable paths (parse failure, path-lookup error, zero paths) ⇒ dropped with a note — scitra is strictly the no-daemon fallback and does not apply here.

Path selection pkg/hev3/pathset.go

selectPathSet: expired paths are excluded; paths expiring within 2s only if nothing else is left; paths whose metadata MTU cannot carry a 1200-octet QUIC datagram plus the SCION (common, address, path) and UDP headers are excluded (SCION dials pin quic-go's InitialPacketSize to 1200 so the check matches). Ranking is greedy (rankGreedy): first the path with the fewest AS hops, then repeatedly the path with the least overlap with those already selected (shared transit ASes, then shared pairs of adjacent ASes, then shared inter-AS links); ties by AS hops, then declared latency (known first), then fingerprint. Paths through an interface in the SCMP down cache (scmpDownCache, 10s TTL) rank after all others.

scionContext — shared daemon state

A scionContext (created per-Fetch by newSCIONContext, shared via DialerOptions.SCION) caches the sciond-derived state every SCION operation needs: one pathQuerier for expansion (querier) and one (connector, topology, local IP) triple for dials (dialParams) — resolved once instead of paying ~3 daemon RPCs per path attempt. The lifecycle details are deliberate:

  • Detached, bounded connects. Each resolution runs under detachedConnectContext: context.WithoutCancel + a 3s timeout (scionContextConnectTimeout). Rationale: a losing race attempt's cancelled ctx must not poison the shared connect for every other attempt; WithoutCancel strips all upstream cancellation (including Fetch's overall timeout), so the 3s bound is the only stop.
  • One-shot failure caching. querier and dialParams each resolve at most once (sync.Once) and cache failures for the context's lifetime — a transient daemon error on the first call disables native SCION for the rest of this Fetch (deliberate trade: correctness over one retry). daemonAddr is frozen at construction.
  • Close-safe by mutex, not Once. Close is guarded by a mutex plus a closed flag rather than its own sync.Once, because independent Once values have no happens-before relationship: a naive Close could run between a connection's RPCs completing and the result being stored, see nothing to close, and leak a live connection the Once then caches. With the mutex, whichever of Close vs. the Once body's final store observes closed second either reaps the just-produced connection (which then surfaces as errSCIONContextClosed) or has nothing left to reap.

dialSCION and the path racer pkg/hev3/racer.go

Native h3 over SCION: get (connector, topology, localIP) — from the shared context when o.SCION != nil (never closing the shared connector), else inline with owned-connection cleanup on every error path — then dialRacing: build an snet.SCIONNetwork whose SCMP handler is a pathRacer, Listen (dispatcherless, concrete local IP, port 0), and dial quic.Transport{Conn: racer}. The racer is a net.PacketConn between quic-go and the snet.Conn: it starts on the top-ranked path, adds the next path when the Path Delay of the most recently added path elapses (pathdelay.go: smoothed RTT plus twice the RTT variation of that path from pathRTTHistory, which Established.Close fills from quic-go's ConnectionStats for the selected path; else four times its declared latency; else 50ms; within [10ms, attempt delay]; a configured delay is fixed, negative = all at once) and at once when every added path has failed, sends each new path copies of the datagrams already sent, and until a path is selected sends every datagram on every added, non-failed path. It selects a path when a datagram from the server, whose first QUIC packet carries one of the client's own connection IDs as its Destination Connection ID, arrives on a path whose hop-field interface pairs (after reversal) match an added, non-failed set path ("reply"), or when quic-go sends its first 1-RTT packet ("1rtt"); afterwards it sends only on that path. SCMP External Interface Down / Internal Connectivity Down errors quoting a datagram sent on a set path fail that path and enter the down cache; when all paths have failed the racer cancels the dial context with errAllPathsFailed. Other SCMP types are ignored; per-packet snet read errors are dropped. The connection ID check matters because snet binds the highest free port of the dispatched range, so successive connections reuse the same local port and late datagrams of the previous connection reach the new socket (counted as recv_foreign). Per-attempt racer stats (RacerStats) are returned in Result.SCIONAttempts. It deliberately does not use pkg/snet/squic: squic wraps the QUIC session as a single-stream net.Conn for control-plane RPC, whereas HTTP/3 needs the raw *quic.Conn. The racer tests (racer_test.go) emulate paths with UDP relays between a real snet client and server.

9. dial_scitra.go — the translator leg pkg/hev3/dial_scitra.go

ScitraMap(ia, host, prefix) encodes a SCION address into its SCION-IP-translator mapped IPv6 address, bit-for-bit identical to the scitra CoreDNS plugin's scion2ip:

[0]      prefix (fc00::/8 by default — scitraPrefixDefault 0xfc)
[1:5]    uint32 (ISD<<20)|asnEnc, big-endian; asnEnc = raw ASN when ASN < 2^19,
         or (1<<19)|(ASN&0x7ffff) for the range 0x2_0000_0000..0x2_0007_ffff;
         any other ASN is unmappable (error). ISD must fit 12 bits.
[5:8]    local prefix / subnet ID — always zero here (plugin TODO defaults)
[8:16]   host: IPv4 as 0x0000ffff‖v4, IPv6 as the low 8 bytes of the v6

scitraAvailable() decides whether the fallback exists at all: it scans the kernel IPv6 routing table for an fc00::/8 entry — destination-field prefix "fc" with prefix length "08". The table path is the package var procNetIPv6Route (/proc/net/ipv6_route), a seam tests point at a fixture; a missing/unreadable table reads as unavailable. dialScitra itself is trivially dialIP: by the time it runs, ExpandSCION has already rewritten Host to the mapped IPv6 literal and cleared the path, so it's an ordinary IP dial over the translator route.

10. dial_ip.go — dispatch & IP dials pkg/hev3/dial_ip.go

NewDialer(DialerOptions) returns the single DialFunc the engine launches, a three-way dispatch on the candidate:

switch {
case c.ViaScitra:              return dialScitra(ctx, c, o)
case c.Family == FamilySCION:  return dialSCION(ctx, c, o)
default:                       return dialIP(ctx, c, o)
}

dialIP picks HTTP/3 (dialH3IP) when offersH3(c.ALPN), else TCP+TLS (dialTCP). dialH3IP opens a fresh UDP socket, dials QUIC, and wraps the connection via newH3Established in an http3.ClientConn RoundTripper whose Close tears down client-conn, QUIC conn, h3 transport, and underlay in order. dialTCP does one TLS dial and returns either an http2.Transport client conn (negotiated h2) or oneConnH1Transport — an http.Transport whose DialTLSContext hands out the already-established conn exactly once and errors on any second concurrent demand (never expected for one winner). TLS configs are cloned per attempt: h3TLSConfig pins ALPN to h3; tcpTLSConfig takes the candidate's ALPN minus h3 (UDP-only), defaulting to h2, http/1.1.

DialerOptions carries the base TLS config, DaemonAddr (precedence in daemonAddress: option → $SCION_DAEMON_ADDRESS → defaultDaemonAddr 127.0.0.1:30255), K, the Timeline, and SCION *scionContext — the shared daemon state; nil means per-call lazy behavior, which is what standalone library callers and older tests get.

11. timeline.go — the event bus pkg/hev3/timeline.go

Timeline is a mutex-guarded append-only list of Event{At, Kind, Label, Detail}; the zero value is ready to use and the start time is set lazily by the first Add, so all timestamps are relative to the first recorded event. Events() returns a snapshot copy. Producers and kinds:

Note that fail is deliberately overloaded: resolver/expansion drop-notes and genuine attempt failures share the kind and are distinguished by their labels' lifecycle (a drop-note's label never gets an attempt).

12. hev3.go — Fetch wiring pkg/hev3/hev3.go

Fetch(ctx, rawURL, Options) glues everything together. In order:

  1. parseTarget: https-only (hev3 speaks only h3/h2 over TLS), port defaulting to 443.
  2. ResolveHost under a child resolveCtx. Its cancel is both deferred and called explicitly right after the engine returns a winner — the draft's §6 MAY: stop outstanding queries once the race is decided. Cancelling resolveCtx is also what unblocks the resolver goroutine if Updates still has unsent merges.
  3. buildTLSConfig: one tls.Config shared by every leg, ServerName pinned to the URL hostname (so the demo CA's *.scion cert verifies identically on SCION, v6 and v4 legs), roots from Options.CAFile or defaultCAFile (/etc/hev3/ca.pem) when it exists, else the system pool.
  4. newSCIONContext(dOpts) with defer sctx.Close() registered before defer est.Close() — LIFO means the connection closes first, then the shared daemon connector. With Options.Session (CLI -repeat) the session's context is used instead and outlives the Fetch.
  5. runEngine with the full dynamic config: sortFn closes over hasSCION(cs) (recomputed per resort — SCION-first ordering ends if every SCION endpoint is dropped or becomes a scitra leg) and the effective PFC; isProto is FamilySCION && Path == nil && !ViaScitra; expand wraps ExpandSCION one candidate at a time.
  6. getOverWinner: one GET over est.RT, body capped at maxBodyBytes = 4096, status prefixed with the proto ("HTTP/2.0 200 OK").
Filter semantics — families only, children exempt. The filter closure implements NoSCION/NoIP against resolved candidates: NoSCION drops FamilySCION, NoIP drops everything else. It is applied by ingest to resolver-delivered candidates only — expanded children are never re-filtered. So under NoIP, a SCION proto's scitra child (which is FamilyIPv6) still races: the scitra leg is the SCION fallback, not an IP candidate. Children inherit the parent's verdict.

Error shape: the engine's noCandsErr is the pre-built "hev3: fetch: no candidates for <host>"; Fetch detects it with errors.Is and returns it un-wrapped, so a no-candidates outcome is not mislabelled as a race failure (everything else gets the "hev3: fetch: race:" prefix).

buildRaceRows quirks. The human race table is derived purely from Timeline events: a label first seen via candidate with no later attempt renders "never-started"; otherwise outcome/timing come from attempt plus whichever of success/fail/cancel (and winner) follows. The one post-processing pass is suppressExpandedProtoRows: every SCION proto gets a candidate event under its un-suffixed label, but attempts only ever fire on the expanded #paths child — without suppression the parent would sit forever as a misleading "never-started" ghost row next to its own children. The rule is precise: drop a never-started, outcome-less row only when some started row's label extends it with #; a genuinely unreachable candidate keeps its row. familyFromLabel maps label prefixes back to family names for display (scitra: → "SCION(scitra)"). 14. cmd/hev3-server — demo target cmd/hev3-server/main.go, listen.go, scion.go, handler.go

Purpose. Serve the same tiny handler over every transport hev3 can win on — h2/http1.1 over TCP+TLS, h3 over IP QUIC, optional cleartext :80, and (with -scion) native h3 over dispatcherless SCION QUIC — tagging each response with the transport (and, for SCION, the peer ISD-AS) that delivered the request.

The server struct pattern (main.go): each listener is a server{name, serve, shutdown}; constructors bind synchronously so the caller logs "listening" only after a real successful bind; serveAll runs every serve loop, waits for SIGINT/SIGTERM or a fatal serve error (ignoring http.ErrServerClosed/quic.ErrServerClosed), then shuts everything down with a 5s grace.

SCION-first setup and the ip-h3 exclusion logic (listen.go, ipH3Addrs). SCION is set up first because its bound underlay IP is the one address the ip-h3 UDP listeners must avoid. Why: dispatcherless SCION pins the underlay UDP port to the fixed SCION port (the zone's SVCB port=443 applies to the SCION leg — not negotiable), and Linux refuses a wildcard UDP bind and a specific-address UDP bind sharing one port unless both set SO_REUSEADDR — which the snet PacketConn does not. So in SCION mode with a wildcard -listen-ip host, ipH3Addrs enumerates the host's addresses (loopback + global unicast; skipping the SCION underlay IP, link-local, and everything in -listen-exclude — e.g. the mgmt IP scitra's port-forwarding binds) and buildH3IPServer binds one UDP listener per remaining address, all served by one shared http3.Server so a single Shutdown closes them all. An explicit non-wildcard -listen-ip host is honored as-is (erroring only if it is the SCION underlay address). The TCP listeners are unaffected — a wildcard TCP bind never collides with a UDP socket.

scionServer (scion.go) mirrors the client dial: sciond connect → topology → underlay IP (scionLocalIP: the -scion-ip flag wins, else sciond-derived; the flag exists because the testbed fabric puts the SCION listener on a sibling .81 address so it can't collide with ip-h3 on .80) → snet.Listen → quic.Transport → http3.Server.ServeListener. localAddr reads the bound IP back from the actual snet.Conn rather than trusting the pre-bind lookup — the lookup is a hint, the socket is the truth. The request's remote address is the snet UDPAddr string, which is how the peer ISD-AS reaches the response body.

Handler transport tagging (handler.go): each listener wraps the shared mux in withTransport(base, h), stashing "scion", "ip-h3", or "ip" in the request context; transportTag reads it back and refines the "ip" placeholder into ip-h2/ip-http/1.1 from the negotiated TLS ALPN, since one TCP listener serves both. GET / returns a plain-text "reached over <transport>" summary; GET /whoami returns the same as JSON plus the request path.

15.2 Forked dependencies (load-bearing)

go.mod replaces one module; the code will not parse SCION SVCB records against the upstream:

  • github.com/miekg/dns → github.com/netsys-lab/dns-scion-svcb — adds the typed scion SvcParamKey the resolver consumes directly: dns.SVCB_SCION and dns.SVCBScion (with SCIONAddr values). Upstream miekg/dns would surface these as opaque unknown params — parseServiceRecord's type switch and the whole SCION discovery path depend on the fork.
  • github.com/scionproto/scion is the upstream release v0.15.1 (no fork); dispatcherless snet.SCIONNetwork + quic-go v0.59.1 on both the client (dialSCION) and the server (scionServer).

15.3 Load-bearing invariants

  • Empty-check post-expansion (sourcesDone). "No candidates" is only decidable once every source is exhausted: the engine's terminal guard requires inflight == 0 && pending empty && !updatesOpen && expanding == 0. An Initial set may legitimately be SCION-proto-only while A is still in flight — declaring failure any earlier would abort a race whose candidates simply haven't materialized yet.
  • Expansion is memoized per label. The proto's table entry (candExpanding/candExpanded) is the memo: a later update re-sending the same proto never re-expands, so Timeline drop-notes stay single and expansion work isn't duplicated across resolver batches.
  • The family filter never touches expanded children. filter runs in ingest against resolver-delivered candidates; expandResults ingestion deliberately skips it. NoIP must not kill the scitra (FamilyIPv6) child of a spared SCION proto.
  • Labels are stable identity. Table membership, tombstoning, timeline dedup, and CLI row-building all key on Label. Rename a label format and you silently break §7 merge semantics and the CLI's proto-row suppression (which depends on the #p suffix convention).
Known caveat — duplicate labels. A label encodes family, host (and the +tcp/#paths/hint variants) but not port or priority. Two ServiceMode records with different TargetNames that resolve to the same IP produce two candidates whose labels collide (e.g. both v6:2001:db8::1) even when their ports or priorities differ; the engine's first-wins ingest keeps the earlier one (the lower-priority record, since records are emitted in §5.2 order) and drops the later silently, and the resolver's timeline dedup likewise reports the label once. Harmless for the testbed zones, but worth knowing before reusing labels as a general-purpose key.

16. Glossary

proto-candidate
A SCION candidate straight out of DNS: FamilySCION, Path == nil, !ViaScitra. Not dialable — a placeholder the engine hands to expansion instead of the pending list.
SCION endpoint candidate / path set
A dialable SCION candidate produced by ExpandSCION: the proto plus its ranked path set (up to K snet.Paths); labelled <parent>#paths. One QUIC connection races the paths of the set.
scitra leg
The SCION-IP-translator fallback: a proto rewritten to its mapped IPv6 address (ScitraMap, fc00::/8), dialed as ordinary IPv6. Exists only when no daemon is reachable but an fc00::/8 route is. Counts as the SCION fallback, not an IP candidate, for filtering.
Resolution Delay
Draft §4.2: the bounded wait (default 50ms, timer armed at the first positive answer) for the owner's AAAA and the service RR answers before releasing Initial candidates built from what has arrived.
Expansion Delay
draft-john-scion-happy-eyeballs: hold the first IP attempt while a path lookup is in flight for a SCION endpoint that would precede it, up to 50ms by default. Implemented as the engine's grace gate (holdForGrace/graceOver), surfaced as -expansion-delay (0 = off).
Path Delay
The wait after adding a path of a path set to the racing QUIC attempt before adding the next: smoothed RTT + 2 × RTT variation of that path (history), else 4 × its declared latency, else 50ms; within [10ms, attempt delay].
attempt delay / stagger
Draft §6: the interval between successive connection-attempt launches. Base default 250ms, hard floor 10ms (MUST), cap 2s default.
adaptive delay
The engine's optional SCION shortcut (off by default): after launching a SCION endpoint whose top path has known latency L, the next stagger is clamp(2L+60ms, min, base) — tighten, never lengthen.
PFC (preferred family count)
-pfc / PreferredFamilyCount: how many candidates the preferred family gets per interleave round before each other family takes one.
RRBoth / RRHTTPS / RRSVCB
Which service-binding RR type(s) the resolver queries. RRBoth (default) queries HTTPS and SVCB in parallel and prefers the HTTPS answer — the migration default while deployed zones still use SVCB.
tombstone
An engine table entry marked candDone without ever launching: its label (or its proto parent) vanished from a later complete update set. Permanent within a run.
dispatcherless SCION
The snet mode (scionproto/scion v0.12+) where the application's UDP socket is the SCION underlay — no dispatcher daemon multiplexes ports. Consequence: the underlay UDP port is pinned, which drives the server's ip-h3 bind-exclusion logic.
sciond / daemon
The local SCION daemon (default 127.0.0.1:30255) that answers path queries and provides topology; its absence triggers the scitra fallback.
ISD-AS / IA
SCION's two-part AS identifier, e.g. 1-150; ASNs above the 32-bit BGP space print as three 16-bit hex groups (71-2:0:4a).
F-numbers (F8, F9, F12, …)
Feature IDs from the local design specs, referenced in code comments (e.g. F9 = resolver failover, F10 = SCION-requires-QUIC, F12 = shared scionContext, F13 = adaptive delay). The specs live in gitignored local-docs/; the comments are self-explanatory without them.
